# Commons as an app

The website stays. The end product is an app on the phone, and this page is the
exact path there, honest about which steps happen in this repo and which need
your own Mac or Android Studio.

| Route | iPhone | Android | Mac | Windows | State |
|---|---|---|---|---|---|
| **Install from the browser** (PWA) | yes | yes | yes | yes | **Working and verified** in CI |
| **App Store / Play Store** (Capacitor) | project generated, icons drawn, tested | project generated, icons drawn, tested | — | — | **Ready to open in Xcode / Android Studio.** Not compiled here — see §2 |
| **Desktop app** (Electron) | — | — | shell reviewed, build configured | shell reviewed, build configured | **Needs Electron installed and a signing certificate** — see §3 |

## The one design decision

**Every app is a window onto one shared Commons, not a copy of one.** Running the
server inside an app would give every person their own empty private community, which
is the opposite of the point. So the iPhone and Android apps load the Commons you
deployed, in a native shell, with the web assets bundled for first paint and the
offline shell cached by the service worker; the desktop app opens the same address in
its own window. One codebase, one server, the website unchanged.

That means **deploy first** (`docs/deploy.md`). The apps need an HTTPS address to load.

---

## 1. Install from the browser — works today

**iPhone / iPad** — open Commons in Safari, tap Share, then *Add to Home Screen*.
**Android** — open it in Chrome; a prompt appears, or use the menu and *Install app*.
**Mac / Windows** — open it in Chrome or Edge and use the install button in the address bar.

You get the icon, a standalone window, instant opens, and a page that explains itself
with no signal. Anything under `/api/` is never cached: yesterday's community shown as
today's would be worse than an error. Requires HTTPS.

## 2. App Store and Play Store

### What is already done, in this repo

- `capacitor.config.ts` — app id `org.commons.app`, name, the night colours for
  splash and status bar, and the server address from `COMMONS_URL`.
- `android/` and `ios/` — the native projects, generated by Capacitor 8. iOS uses
  Swift Package Manager, so there is no CocoaPods to install.
- Icons and splash screens for both, at every size each platform asks for, drawn from
  the same mark as the web icons by `scripts/app-assets.mjs` — no image tooling, no
  placeholder art left anywhere. The iOS 1024 icon is written without an alpha
  channel, which App Store Connect otherwise rejects (ITMS-90717).
- `npm run app:sync` — copies the web assets in, bakes the server address into both
  projects, writes it into the iOS plist as an app-bound domain (without that, the
  offline shell's service worker silently does not run inside the app), and redraws
  the assets. Safe to re-run; CI runs it.
- `test/apps.test.ts` — 15 checks: the config, the projects, every icon and splash
  size, the opaque iOS icon, the app-bound domain, the desktop shell.

### What happens on your machine

```bash
# once the site is up at its real address
COMMONS_URL=https://commons.yourdomain.org npm run app:sync
npm run app:android      # opens Android Studio
npm run app:ios          # opens Xcode (Mac only)
```

**Android → Play Store**
1. Android Studio: let it sync Gradle and download the SDK it asks for.
2. *Run* on an emulator or a phone — the app opens your Commons.
3. *Build → Generate Signed Bundle* (.aab). Create the upload key once; keep it safe —
   losing it means a new app listing.
4. Play Console: create the app, upload to **Internal testing** first (up to 100
   testers, no review), then Production.

**iPhone → App Store**
1. Xcode: *Signing & Capabilities* → pick your team.
2. *Run* on the simulator or a phone.
3. *Product → Archive* → *Distribute* → **TestFlight** (up to 10,000 testers, light
   review) → then App Store.

### What both stores will ask for

- Developer accounts: Apple $99/year, Google $25 once.
- A privacy policy URL. Say plainly what is stored: username, email, phone, what
  people post; never an identity document; email and phone never shown to other
  members.
- Screenshots (phone and, for Apple, iPad), a description, an age rating.
- **Apple guideline 4.2 — "more than a website".** The honest answer, which is also
  true: the app installs with its own icon and splash, opens with no signal on the
  cached shell, keeps a signed-in session, lights up live when somebody answers, and
  tells people when somebody answers their question. Notifications inside the store
  app itself need the native route in §4; until then that last claim is true of the
  home-screen install, not the Capacitor build.

### While developing

`COMMONS_URL=http://192.168.1.20:3000 npm run app:sync` points the app at a laptop on
the same wifi and turns cleartext on for that build only. Never ship one.

## 3. Mac and Windows

`desktop/main.js` is an Electron shell: `nodeIntegration: false`, `contextIsolation:
true`, `sandbox: true`, off-site links open in the real browser. On first run it asks
which Commons to open and remembers it; `COMMONS_URL` skips the question. The
`electron-builder` configuration is in `package.json` under `build`.

Electron is **not** a dependency of this repo — it is a 100 MB binary that every
`npm ci`, including CI's, would download for no reason. Install it when you want it:

```bash
npm install --no-save electron electron-builder
npm run desktop                          # run it
npx electron-builder --mac               # on a Mac: .dmg and .zip
npx electron-builder --win               # on Windows: an installer
```

Shipping it needs code signing — an Apple Developer ID certificate, a Windows
Authenticode certificate — or both operating systems warn people away from opening it.
Not run where this was written: no Electron binary, no Mac, no Windows.

## 4. Notifications — built, Web Push

Turned on from a member's own page, per device. Four moments: somebody answered your
question, somebody said your answer worked, somebody said hello, a message about a
get-together arrived. Never room chatter, never across a block, never a private message's
text. `npm run push:keys` makes the key pair the server needs (`docs/deploy.md`).

Where it works today:

| | Website / installed from the browser | Store app (Capacitor) |
|---|---|---|
| Android, Chrome | yes | **no** — the Android WebView has no push service |
| iPhone | yes, **once added to the home screen** (iOS 16.4+); the card says so in Safari | **no** — WKWebView has no push service |
| Mac / Windows, Chrome or Edge | yes | — |

So the store apps are the one place notifications do not yet reach. The next step there
is native push: the `@capacitor/push-notifications` plugin, Firebase Cloud Messaging for
Android and an APNs key for iOS, and a second sender on the server that talks to those
instead of a browser's push service. The subscription table, the four moments and the
copy are already in place; that step adds a delivery route, not a feature.

---

## What to do first

Deploy the website. Then `npm run app:sync` with the real address, open the Android
project, and put a build on your own phone the same day. Internal testing on Play and
TestFlight on iOS need no store review; that is where the first real members can come
from while the listings are prepared.
